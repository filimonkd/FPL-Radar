# Deployment runbook (Step 12)

This runbook covers production: MongoDB Atlas M0 and one Render free web service, which serves the API and the built client from the same origin. The design is in `ARCHITECTURE.md` §11 and the checklist in §17.3; this file lists the exact steps and the checks that go with them.

Everything here runs from your own accounts. The development environment that built this code can't reach Atlas, Render or the FPL API.

## 0. What production looks like

| Item | Value |
|---|---|
| Runtime | Node 22 (`.node-version`); Express 5; Mongoose 9.10 (its own MongoDB driver 7.x); MongoDB **8.0** (Atlas M0; local and tests pinned to 8.0) |
| Service | One Render free web service, region **Frankfurt**, from `render.yaml` |
| Build | `npm ci --include=dev && npm run build`. `--include=dev` is needed because `NODE_ENV=production` also applies at build time, and plain `npm ci` would then skip Vite and Tailwind. |
| Start | `npm start` → `node src/server.js`: validate env (exit 1 listing every problem) → connect (10 s server selection) → boot migrations under the `migrate` lease → listen on `$PORT` |
| Health | `GET /api/health`: 200 `ok` only when all of these hold; otherwise 503 `degraded`. Every request re-evaluates, so recovery is automatic.<br>• DB ping OK<br>• every migration applied<br>• env valid<br>• not shutting down |
| Frontend → API | Same origin. The SPA calls `/api/...` with relative URLs. Express serves `client/dist`: hashed `/assets/*` are immutable for 1 year, `index.html` is `no-cache`, and non-`/api` GETs fall back to `index.html`. Vite's dev proxy only exists locally. |
| CORS | None. Cross-origin requests get no `Access-Control-Allow-*` headers. |
| Cookies | Admin session `fpl_admin`: `HttpOnly; Secure; SameSite=Strict; Path=/api`, 12 h JWT. Viewers use `X-Share-Token`. |
| Headers | helmet defaults: CSP `default-src 'self'`, HSTS, nosniff, `frame-ancestors 'none'`. `x-powered-by` is off. |
| Proxy | `trust proxy = 1`: Render's single TLS-terminating hop, so the login rate limit (10 per 15 min per IP) sees the client IP. |
| Keep-warm | cron-job.org → `POST /api/internal/tick` with header `X-Tick-Secret`, every 10 min. It returns 204 and starts nothing. |
| Shutdown | SIGTERM:<br>1. stop accepting requests<br>2. mark this process's running syncs `ABANDONED`<br>3. release their leases<br>4. disconnect<br>5. exit 0 (forced exit 1 after 10 s) |

### Environment variables (Render)

| Variable | Value | Source |
|---|---|---|
| `NODE_ENV` | `production` | `render.yaml` |
| `MONGODB_DB` | `fpl_rival` | `render.yaml` |
| `MONGODB_URI` | `mongodb+srv://app:<password>@<cluster>/?retryWrites=true&w=majority`. Use the `app` user with the custom role only, and no database in the path. | Dashboard (`sync: false`) |
| `ADMIN_PASSWORD_HASH` | bcrypt hash from `npm run auth:hash` (never the password) | Dashboard (`sync: false`) |
| `JWT_SECRET` | 32+ random chars | Generated by Render |
| `TICK_SECRET` | 32+ random chars; also paste it into the cron-job.org header | Generated by Render |
| `PORT` | set by Render | Render |
| `FPL_API_BASE_URL` | unset (defaults to the public FPL API) | – |

Production boot fails, listing every problem, if any of these is true:
- `JWT_SECRET` is shorter than 32 characters or is `change-me`;
- `ADMIN_PASSWORD_HASH` is missing or isn't a bcrypt hash;
- `TICK_SECRET` is missing or shorter than 32 characters;
- `MONGODB_URI` or `MONGODB_DB` is invalid.

Values are never echoed, only the variable names.

## 1. Validate config (before any deploy)

1. CI is green on the commit you'll deploy. CI runs build → bundle scan → unit → integration; the integration suite includes the production-process test.
2. Locally, confirm production config is rejected when incomplete:
   ```bash
   NODE_ENV=production MONGODB_URI=mongodb://x MONGODB_DB=fpl_rival JWT_SECRET=change-me node server/src/server.js
   # → "Invalid environment:" listing JWT_SECRET, ADMIN_PASSWORD_HASH, TICK_SECRET; exit 1
   ```
3. Create the admin hash: `npm run auth:hash` (the password is read without echo). Keep the password in a password manager.
4. Check that the client bundle holds no secrets: `npm run build && npm run check:bundle`.

## 2. Atlas (once)

Follow §17.3 "Atlas":
1. Create project `fpl-rival` and an **M0 in AWS eu-central-1 (Frankfurt)**. Record the version shown; it should be 8.0.x.
   - If Atlas shows 8.1 or later, pin `docker-compose.yml` and `server/package.json` `config.mongodbMemoryServer.version` to it in a separate change.
2. Create custom role **`fplAppRole`** (Atlas UI → Database Access → Custom Roles) on `fpl_rival`:
   - `find`, `insert`, `update`, `remove` on every collection **except** `resultSnapshots` and `gwResultActions`, which get `find` and `insert` only;
   - `createCollection`, `createIndex`, `collMod`, `listCollections`, `listIndexes` for the boot migrations.
3. Create the database users, each with a random 32+ character password:
   - **`app`**: `fplAppRole` only. No built-in `readWrite`, because Atlas grants the union of a user's roles and `readWrite` would override the restriction.
   - **`backup-ro`**: built-in `read` on `fpl_rival`.
   - **`admin-ops`**: `readWriteAnyDatabase`, kept only in a password manager.
4. **Network access:** leave it empty for now. Never add `0.0.0.0/0` or standing personal IPs.
5. Create a programmatic API key with **Project Network Access Manager** for the backup workflow.
6. Set alerts: connections > 400, storage > 60%.

## 3. Render: deploy the backend and the client

1. Render → New → Blueprint → this repository. It reads `render.yaml` and creates the service in **Frankfurt**.
   - `autoDeployTrigger: checksPass` means only commits whose CI passed are deployed.
2. Enter the `sync: false` values: `MONGODB_URI` (the `app` user) and `ADMIN_PASSWORD_HASH`.
3. **Atlas access list:**
   1. Open Render → the service → **Connect → Outbound** and copy every CIDR range.
   2. In Atlas → Network Access, add each range with the comment `render-frankfurt`.
   - These ranges are shared by every Render service in the region. The real boundary is SCRAM auth, TLS and the least-privilege role.
   - Re-check the ranges if the service ever moves region.
4. Deploy, or redeploy after adding the ranges. The first boot applies every migration under the `migrate` lease. The log shows:
   ```
   MongoDB connected (db: fpl_rival)
   Migrations: N applied, 0 already applied
   Server listening on …
   ```
5. **Verify DB and migrations:**
   ```bash
   curl -s https://<service>.onrender.com/api/health
   # expect: status "ok", env "production", checks.migrations { ok: true, applied: N, expected: N, pending: [] }, checks.runtime.ok true
   ```
6. **Verify the audit role:**
   1. Connect as `app` from a laptop through a temporary access entry (`atlas accessLists create --currentIp --deleteAfter <now+1h>`).
   2. Run `db.gwResultActions.updateOne({}, {$set:{x:1}})` and expect `not authorized`.
   3. Delete the entry.

## 4. Verify end to end, then smoke

1. **Deploy smoke.** It is read-only and makes no FPL calls:
   ```bash
   TICK_SECRET=… SMOKE_ADMIN_PASSWORD=… npm run smoke:deploy -- https://<service>.onrender.com 2026-27
   ```
   It checks:
   - health (ok, production, migrations applied, not draining);
   - the SPA from the same origin with CSP and HSTS, and no CORS;
   - a JSON 404 for unknown `/api` paths;
   - anonymous 401;
   - tick with a wrong secret (401) and with the real one (204);
   - admin login cookie flags, `/api/auth/me` and `/api/status`, then logout.

   Every line should read `PASS`; the script exits 1 otherwise. It prints no secrets.
2. **cron-job.org:** `POST https://<service>.onrender.com/api/internal/tick` every 10 min with header `X-Tick-Secret: <TICK_SECRET>`. Expect 204; 401 means the secret doesn't match.
3. **FPL smoke (Step 2):** run the `FPL smoke test` workflow (Actions → workflow_dispatch) against both real leagues before creating groups. It runs on a GitHub runner, never in this development environment.
   - Review the anonymized artifact.
   - Commit only what the report policy allows.
4. **Go-live** (§17.3):
   1. Create Group A and Group B in the UI.
   2. Run a sync.
   3. Check the Status page request log and storage gauge.
   4. Finalize one finished gameweek.
   5. Open the History drawer and confirm the chain badge is valid.
5. **db:check against production** through a temporary access entry:
   ```bash
   atlas accessLists create --currentIp --deleteAfter "$(date -u -d '+1 hour' +%Y-%m-%dT%H:%M:%SZ)"
   MONGODB_URI='mongodb+srv://backup-ro:…@…/' MONGODB_DB=fpl_rival npm run db:check   # expect "ok": true, counts.error 0
   atlas accessLists delete <your-ip> --force
   ```

## 5. Backups (GitHub Actions `backup.yml`)

1. **Keys:**
   1. Generate them: `age-keygen -o backup.key`.
   2. Store `backup.key` (the private key) only in your password manager, then delete the file.
   3. Commit the public key line (`age1…`) as **`ops/backup.pub`**.

   The workflow refuses to run without it; no placeholder is committed.
2. **Repository secrets:**
   - `ATLAS_PUBLIC_KEY`, `ATLAS_PRIVATE_KEY`: the programmatic key from §2.5;
   - `ATLAS_PROJECT_ID`;
   - `BACKUP_RO_URI`: `mongodb+srv://backup-ro:…@<cluster>/`, with no database in the path.

   Optional repository variable: `MONGODB_DB` (default `fpl_rival`).
3. Run **Backup** manually once (Actions → Backup → Run workflow), then check:
   - the "Temporary Atlas access entry" and "Remove the Atlas access entry" steps both pass, and the removal runs even if something fails;
   - every collection is dumped and restored into `mongo:8.0`;
   - db:check prints `{"ok":true,…}`. It prints counts only; the full report is inside the encrypted archive;
   - the artifact is named `fpl-rival-<date>-dbcheck-ok` and kept for 90 days.
4. **Test a restore:**
   ```bash
   age -d -i backup.key -o backup.tar fpl-rival-<date>.tar.age
   tar -xf backup.tar
   mongorestore --gzip --archive=<collection>.gz
   ```
   Run the restore into local `mongo:8.0`, once per collection.
5. It then runs weekly on Monday at 06:00 UTC. A red run means either the dump failed or db:check found errors; the artifact still holds `dbcheck.json`.

## 6. Rollback and restart

- **Restart** (Render → Manual Deploy → Restart, or any redeploy):
  - Render sends SIGTERM. A sync in flight is marked `ABANDONED` and its lease released, and it can't commit afterwards (the fence fails).
  - The next boot applies 0 migrations (`N already applied`) and serves the same state.
  - A crash without SIGTERM is covered by lease expiry: 120 s, after which the next acquirer marks the run `ABANDONED`.
  - The integration test `server/test/integration/production.test.js` exercises this with a real process.
- **Rollback:** Render → Deploys → pick the previous deploy → Rollback. Migrations are additive and idempotent (`createIndexes` and `collMod` with validators), and nothing is reapplied once it's recorded. An older build checks only the migrations it knows about, so its health stays green.
  - Before rolling back across a migration that tightened a `$jsonSchema` validator, check that the older code's writes still pass it. Today every migration only adds.
  - **Never** roll back by restoring a backup over live data. A restore is for disaster recovery only (§5), done with `admin-ops` through a temporary access entry.
- **Deleting data:** there is no delete path in the application; TTL on provenance documents is the only deletion (`ARCHITECTURE.md` §9). Don't hand-edit `resultSnapshots` or `gwResultActions`: the app role can't, and `db:check` I4 and I5 would flag it.

## 7. Monitoring

- **Render logs:** plain lines with no request bodies, cookies, JWTs, share tokens, passwords or raw FPL responses. 5xx errors log method, path (never the query string) and a redacted error (`server/src/utils/redact.js`).
- **`/api/status`** (admin): recent runs with their request logs, points semantics, the chip-rule source, smoke verdicts, and the storage gauge against the 512 MB M0 quota, warning at 60%.
- **Atlas alerts:** connections, and storage at 60%.
- **Health:** Render restarts the instance when `/api/health` keeps failing. A 503 from a shutting-down instance is expected during a deploy.
